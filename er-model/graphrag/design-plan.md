## 1. 构建目标、适用场景与成功标准

### 1.1 背景问题

`er-model/` 已把 1322 张表（A 级 349 / B 级 853 / C 级 120）、18 个业务域、逐表全字段逻辑模型、五级证据推断关系、A–G 七类 30 条模型质量问题，固化为高质量 Markdown + Mermaid 资产。但这些是**静态文档**，存在三类检索痛点（`PLAN.md` §1.1 同样指出）：

1. **跨文档多跳查询困难**：如「改了 `jf_sales_order.status` 会影响哪些下游表和字段」需人工跨 `01-ER图/D01`、`03-逻辑数据模型/*`、`05` 多文件拼接。
2. **实体/关系语义分散**：同一实体（如 `jf_trader`）在 D08 定义、在 D01/D03/D04/D13 被引用，缺乏统一可遍历的图。
3. **证据强度无法量化检索**：关系带 `[注释明示]/[索引佐证]/[命名推断]/[语义推断]/[待确认]` 五级，文档里是文本标签，无法按置信度过滤/排序。

### 1.2 三种技术路线的定位

| 路线 | 核心机制 | 在本项目的适配度 | 采用策略 |
|---|---|---|---|
| **GraphRAG** | 把语料抽取为「实体-关系-属性」知识图谱 + 社区摘要，检索时结合图遍历 + 向量 | 高：`er-model/` 天然是半结构化图谱（表=实体、FK 线索=关系、字段=属性、域=社区分区） | **主线方案**：将 Markdown 资产转建为属性图 + 向量索引 |
| **AgenticRAG** | 由 LLM Agent 规划多步检索/工具调用（查图、查文档、查 DDL）再综合回答 | 高：多跳血缘/影响分析天然需要「先查邻居→再查字段→再汇总」的分步推理 | **叠加层**：在 GraphRAG 之上提供查询规划 Agent |
| **「更好的 RAG」技术方案** | 针对本场景的混合检索 + 结构化 grounding + 证据可溯 | 高：纯向量 RAG 会 hallucinate 出不存在的外键关系，必须用结构化约束兜底 | 作为设计原则贯穿：见 §1.3 |

> **推荐落地形态**：以 **GraphRAG 为知识底座**（属性图 + 向量 + 社区摘要）、**AgenticRAG 为查询编排层**（分步规划 + 工具调用）、并以「**结构化 grounding + 证据分级 + 拒绝臆造**」为「更好的 RAG」核心质量原则。三者不是互斥选项，而是分层组合。

### 1.3 「更好的 RAG」在本场景的具体内涵（质量原则）

1. **Grounding 强约束**：每个答案的表/字段/关系必须能回溯到 `er-model/` 具体文件与行、或图谱节点 ID；无出处的断言必须显式标 `[推断]`/`[待确认]`，绝不臆造外键（呼应全库 0 外键现实）。
2. **混合检索**：向量召回（语义）+ 图遍历（结构/多跳）+ 关键词/BM25（精确表名字段名）三路融合，而非单一向量。
3. **置信度可解释**：关系边携带 `evidence_level` + `confidence`，答案附「证据强度」，低置信度关系默认降权并提示人工确认。
4. **结构化优先于自由文本**：能用图查询回答的（查表/查关系/查血缘）不用纯 LLM 生成，LLM 只做规划与最终自然语言合成。
5. **可评测**：建立黄金问答集（覆盖六类查询），对准确率/召回/幻觉率做回归。

### 1.4 适用场景（Use Cases）

- **UC1 查表**：按业务含义/域/关键字定位候选表（「哪些表存贸易商额度」）。
- **UC2 查字段**：给定表列出字段全列及含义，或反向「哪个表有 `sales_order_id`」。
- **UC3 查关系**：两表之间有无推断关系、经哪种证据、基数如何。
- **UC4 查影响**：某表/字段变更的下游受影响对象清单（影响分析）。
- **UC5 查血缘**：以 `jf_sales_order` 为枢纽的正向/反向多跳血缘链路。
- **UC6 按业务域检索**：域内实体/关系/质量问题的聚合问答与摘要。

### 1.5 成功标准（可衡量，初设 **[待确认]** 阈值需业务方确认）

| 维度 | 目标 |
|---|---|
| 覆盖完整性 | 图谱节点/边数量与 `er-model/` 交付口径可对齐校验（A 级 349 表 + 关系边 + 字段全量，误差为 0 或可解释） |
| 检索质量 | 六类查询黄金集 Top-3 命中率 ≥ 90% **[待确认]** |
| 幻觉控制 | 关系类回答「有出处率」100%；无证据断言全部显式标注 |
| 多跳能力 | 3 跳内血缘/影响查询可正确遍历并给出路径 |
| 可解释性 | 每条关系回答附证据分级 + 来源文件（可定位到 `test_erp.sql` 行优先） |
| 响应时延 | 单跳检索 P95 < 2s，多跳血缘 P95 < 8s **[待确认]** |

### 2.2 A/B/C 分级在图谱中的取舍策略

| 级别 | 表数 | 图谱处理策略 | 理由 |
|---|---|---|---|
| **A 级**（`jf_` 业务 332 + OT 17 = 349） | 349 | **完整入图**：表节点 + 字段节点 + 关系边 + 域归属 + 证据。作为问答主语料 | 逐表全字段 + ER 关系齐备，信息密度最高 |
| **B 级**（`lcap_` 450 + Quartz 275 + Activiti 128 = 853） | 853 | **代表入图 + 族归约**：每个同构结构族展开 1 个代表节点，附 `family=quartz/activiti/lcap` 与 `member_count` 属性；其余成员登记为「族清单」（可查不逐一建字段节点）；默认检索**降权/可开关** | 同构副本，全量入图会使节点膨胀、噪声淹没业务查询（`05` G-3 表数膨胀问题） |
| **C 级**（备份 117 + 测试 3 = 120） | 120 | **默认排除入图**：仅建轻量「影子节点」（表名 + `tier=C` + `source_table` + 排除理由），不参与血缘/影响遍历；提供 `include_c=true` 显式开关 | 快照副本非独立实体（`04` 第一节），入图会造成虚假重复边 |

- **OT 内疑似临时表**（`entity1/entity12345/seq_10/sheet1/temp`）：属 A 级但标 `suspected_legacy=true`，检索降权并保留「待确认」提示（`00` 第四节 OT 说明）。
- **跨域桩实体**（ER 图中带 `[跨域·Dxx]` 的引用，如 D01 中的 `jf_customer`）：**不重复建节点**，通过 `domain` 属性指向其定义域，边指向同一规范节点（避免同名异节点）。

### 2.3 导入范围与边界

- 本期**只建模到「表级血缘 + 字段属性」**，不做数据内容级血缘（无实际 ETL 解析，与 `PLAN.md` 非目标一致）。
- 字段级「影响/血缘」基于 `xxx_id`/`xxx_code` 命名与注释推断，非物理 FK（全库 0 外键）。

## 3. 图谱 Schema 设计

采用**属性图（Property Graph）**模型。以下为设计草案（节点标签 / 边类型 / 关键属性），非最终 DDL。

### 3.1 节点标签（Node Labels）

```
Domain      业务域          { domain_id: "D01", name: "销售订单域", table_count: 18, tier: "A" }
Table       表/实体         { table_id, name: "jf_sales_order", domain: "D01", tier: "A|B|C",
                              prefix_family: "jf|lcap|N{hex}|P{hex}|none|bak|test",
                              pk_columns: [...], has_pk: true, column_count: 90,
                              certified: false, suspected_legacy: false, note }
Column      字段            { column_id, table_id, name: "customer_id", data_type: "bigint",
                              nullable: false, default: null, key_role: "PK|UK|FK|none",
                              semantic: "客户id", charset, collation }
Concept     业务概念/术语   { term: "贸易商", category: "master|transactional|config" }
                            （来自 05 第二节核心实体三分类）
Issue       模型质量问题    { issue_id: "A-1", category: "A..G", title, severity, scope }
                            （来自 05 第三节 A–G 30 条）
EvidenceSrc 证据来源        { source: "01-ER图/D01 | 03-.../D01 | test_erp.sql", locator: "L171" }
```

- **影子节点**（B/C 级非展开成员）：`Table` 打上 `tier` 与 `expanded=false`，B 级额外带 `representative_of` 指回族代表。

### 3.2 边类型（Relationships）

```
(table)-[:BELONGS_TO_DOMAIN]->(domain)
(column)-[:IS_COLUMN_OF]->(table)
(table)-[:RELATES_TO {
    cardinality: "1:1|1:N|N:M",
    direction: "parent|child",
    via_column: "sales_order_id",
    evidence_level: "comment_explicit|index_backed|name_inferred|semantic_inferred|unconfirmed",
    confidence: 0.0-1.0,
    is_inferred: true,
    cross_domain: false,
    source_ref: EvidenceSrc
}]->(table)
(column)-[:REFERENCES {evidence_level, confidence}]->(column)   // 字段级 FK 线索（可选细粒度）
(concept)-[:REALIZED_BY]->(table)
(table)-[:HAS_ISSUE]->(issue)
(edge/relation)-[:SUPPORTED_BY]->(evidenceSrc)                  // 每条边可回溯
(table)-[:DERIVED_FROM]->(table)   // C 级备份/测试表 → 源表；副本 copy1 → 主表
(table)-[:SAME_FAMILY_AS]->(table) // B 级同构族关系
```

- **`RELATES_TO` 是核心边**，承载「关系 + 基数 + 证据 + 置信度」四要素，直接来自 ER 图关系线格式：
  `A ||--o{ B : "1:N [命名推断] a.col -> b.id"`（见 `01-ER图/D01` L171–L200）。
- **自关联边**（如 `jf_sales_order.exchange_order_no -> order.order_no` 换货自关联 L176）需支持 `direction=self`。
- **多态外键**（`flow_change_record.related_order_id` 按 `order_type` 指向多表，`05` A-3）建模为 `[:RELATES_TO {polymorphic:true, discriminant:"order_type"}]`，指向多个候选目标边并共享 `unconfirmed` 级。

### 3.3 关键设计原则

1. **规范身份 `table_id` 稳定唯一**（对标 `PLAN.md` `asset_urn`），用于跨版本 diff 与去重；同名跨域引用汇聚到同一节点。
2. **字段合并行还原**：逻辑模型对「审计四件套」做了合并行（`03-.../D01` L82/L156/L170），入图须**拆回原子列**，否则列数与物理 DDL 不符（`PLAN.md` 评审#1）。
3. **域作为社区分区**：`Domain` 天然对应 GraphRAG 的社区（community）划分，用于社区摘要与「按域检索」。B 级按族、OT 单列特殊社区。
4. **证据节点独立**：把 `EvidenceSrc` 建成一等节点，使「答案可回溯到文件/行」成为图上的可查询关系。

## 4. 从 Markdown / ER / 逻辑模型抽取知识元素的策略

采用**确定性解析为主、LLM 辅助抽取为辅**的混合管线（structured-first，最大化「零臆造」）。

### 4.1 确定性抽取（规则解析器，优先）

| 目标元素 | 抽取来源 | 抽取方法 |
|---|---|---|
| 域成员与表数 | `00` 第四节逐域清单 | 解析「域号\|业务域\|表数」表 + 各 `### Dxx` 下的逗号分隔表名 → `Domain`/`BELONGS_TO_DOMAIN` |
| 表→字段全列 | `03-逻辑数据模型/*` 的 7 列表格 | 按 `| 字段 | 类型 | 可空 | 默认 | 键 | 含义 |` 解析 Markdown 表格 → `Column` + `IS_COLUMN_OF`；键列正则提取 `PK/UK/FK[目标·依据]` |
| 关系边 + 基数 + 证据 | `01-ER图/*` 的 Mermaid 关系线 | 正则解析 `A <rel> B : "描述"`（`||--o{`/`||--||`/`||--|{`），从描述抽 `[证据]`、`a.col -> b.id`、`1:N` → `RELATES_TO` |
| 跨域引用/桩 | ER 图实体块 `[跨域·Dxx]` | 识别桩定义，边目标解析到其定义域规范节点 |
| A–G 质量问题 | `05` 第三节分类列表项 | 解析 `### A..G` + `- **A-1 ...**` → `Issue` 节点 + `HAS_ISSUE`（按 scope 关联表/列） |
| 备份/测试→源表映射 | `04` 第三节表格「表名\|源表」 | 解析表名拆分 `_bak_<时戳>` / `test_` 前缀还原源表 → `DERIVED_FROM`，建影子节点 |
| B 级族归约 | `00` 第八节 8.1 前缀分布 + `01/03` 的 B 级文件 | 按 `N{hex}_`/`P{hex}_`/`lcap_` 前缀与结构族归并 → `SAME_FAMILY_AS` + `member_count` |

> 抽取脚本应复用 `skills/mysql-ddl-data-modeling/scripts/` 的普查思路（`ddl_census.ps1` 前缀分布、`group_by_domain.ps1` 有序正则归域），保持数量口径一致。**注意**：这些脚本面向 PowerShell 5.1/Windows（`Agents.md` §6），当前 macOS 需 `pwsh`，且 Windows 路径需注意兼容 **[待确认]**。

### 4.2 LLM 辅助抽取（受限、需 grounding）

仅用于规则难以覆盖的**语义字段**：
- 字段业务含义的规范化（把「客户id」归一为可检索语义标签）；
- 概念/术语抽取与到表的绑定（`05` 三分类作为种子）；
- 社区摘要生成（GraphRAG community summary）。

约束：LLM 输出**不得新建确定性来源没有的表/字段/关系**；所有 LLM 产出的边必须回填 `SUPPORTED_BY` 指向原文，无法定位者强制降级为 `[待确认]`。禁用 LLM 推断外键方向/基数/目标（呼应 `er-model` 已有的「零臆造陷阱」经验）。

### 4.3 向量与索引层

- **文档块向量**：对 `er-model/*.md` 按「表段落/域段落/问题条目」切块 embedding，支撑语义召回与自然语言问答。
- **节点文本向量**：`Table.name + 域 + 含义摘要`、`Column.name + semantic` 建向量，支撑「按业务含义找表/找字段」。
- **关键词索引（BM25/全文）**：表名/字段名精确匹配（`jf_`、拼写固化名如 `catregory/datat_dict` 需原样可搜）。
- **图索引**：邻接表 + 路径查询，支撑多跳遍历。

### 4.4 抽取校验（数量等式护栏）

沿用 `Agents.md` §7「数量口径硬校验链」，抽取后断言：
- 入图 A 级表节点 = 349；B 级族展开代表 + 归约成员 = 853；C 级影子节点 = 120；合计 1322。
- 每域表数 = `00` 第四节声明值；关系边两端表均存在于图中（无悬挂边，除非目标为 `[待确认]`）。
- 任一断言失败 → 阻断入库并报告，不交付。

## 5. 证据分级与置信度表达

### 5.1 五级证据 → 置信度映射（初设 **[待确认]**）

沿用 `00` 第六节、`05` 开头的五级证据体系（强度降序）：

| 证据级（er-model 标注） | 图谱 `evidence_level` | 置信度区间 | 检索默认策略 |
|---|---|---|---|
| `[注释明示]`（COMMENT 点名目标表） | `comment_explicit` | 0.85–0.95 | 强，正常召回 |
| `[索引佐证]`（`_id`/`_code` 建 INDEX/UNIQUE 且指向 PK） | `index_backed` | 0.7–0.85 | 强，正常召回 |
| `[命名推断]`/`[字段命名]`（`xxx_id` 命名） | `name_inferred` | 0.45–0.7 | 中，标注推断 |
| `[语义推断]`（仅业务语义） | `semantic_inferred` | 0.2–0.45 | 弱，降权 + 警示 |
| `[待确认]`（目标不存在/指向不明） | `unconfirmed` | 0.0–0.2 | 默认过滤，`show_uncertain=true` 才显示 |

- **本库无 `[显式外键]`**（全库 0 FK，`00` 第一节），故最高只到 `comment_explicit`，任何边 `is_inferred=true`。答案须显式声明「关系为逆向推断，非物理外键」。
- **复合证据**：ER 常见 `[命名推断+索引]`、`[注释明示→外部系统]`（如 D15 `crm_complaint_code` 指外部系统而非本库，见 `00` 复核批①）。前者取较高档并记 `evidence_tags=[name,index]`；后者标 `external_reference=true` 且不建本库边（避免虚假关系）。

### 5.2 置信度在检索与回答中的用法

1. **过滤**：默认只召回 `confidence ≥ 0.45`（命名推断及以上）的边；用户可放宽。
2. **排序**：多跳遍历时按边置信度加权，优先高证据路径，避免经低置信边「短路连边」产生假血缘。
3. **回答标注**：每条关系回答附 `evidence_level` 标签 + 置信度 + 来源文件行；多证据冲突时列出全部并标「以 ER 为准」。
4. **人工确认闭环**：`unconfirmed`/`semantic_inferred` 边进入「待确认队列」，人工确认可上调 `evidence_level`（对标 `PLAN.md` M5.4 推断确认台）。`05` 中列明的高危项（B-4 同名列异指向、A-3 多态外键、G-4 迁移遗留）默认进队列。

## 6. 检索与查询设计（六类核心能力）

统一由 **AgenticRAG 查询规划器** 分派到「图查询 / 向量检索 / 关键词」三类工具，LLM 负责规划与最终自然语言合成。

| 能力 | 查询模式 | 主要工具 | 图谱/检索支撑 |
|---|---|---|---|
| **查表** | 「哪些表存贸易商额度」 | 向量召回 `Table` + 域过滤 + BM25 表名 | §4.3 节点向量；`Domain`/`tier` 过滤 |
| **查字段** | 「`jf_sales_order` 有哪些字段」/「哪个表有 `sales_order_id`」 | 图遍历 `IS_COLUMN_OF` / 反向索引 | `Column` 属性 + REFERENCES 反查 |
| **查关系** | 「`jf_sales_order` 与 `jf_invoice` 有无关系」 | 图 1 跳邻居查询 + 证据读取 | `RELATES_TO` + `evidence_level` + `SUPPORTED_BY` |
| **查影响** | 「改 `status` 字段影响哪些下游」 | 图反向可达（BFS/DFS，按置信度加权剪枝） | `REFERENCES`/`RELATES_TO` 反向遍历 + 深度上限 |
| **查血缘** | 「以 `jf_sales_order` 为枢纽的销售→资金链路」 | 多跳路径查询 + 社区摘要 | `Domain` 社区 + 跨域子图（`05` 5 张图作骨架） |
| **按业务域检索** | 「D14 字典域有哪些实体和质量问题」 | 社区分区 + `BELONGS_TO_DOMAIN` + `HAS_ISSUE` | `Domain` 社区摘要 + Issue 聚合 |

- **多跳预算**：默认 ≤ 3 跳，超限返回截断并提示（对标 `PLAN.md` 血缘 ≤ 200 节点渲染策略）。
- **回答结构**：结论 + 依据表（关系/证据级/置信度/来源文件行）+ 不确定项列表。
- **拒绝臆造兜底**：若图中无相应路径/节点，回答必须为「文档未记载/待确认」，不得由 LLM 生成未 grounding 的关系（这是「更好的 RAG」的关键防线，呼应全库 0 外键易致假连接的现实）。
